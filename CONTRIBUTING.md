# Contributing to md3

Thanks for your interest. md3 is built in the open from a written specification, and every change is traced back to it. This page explains how to set up, how commits and pull requests are structured, and how decisions change.

## Before you start

- **The spec is [docs/DECISIONS.md](docs/DECISIONS.md).** Every change implements or touches numbered decisions there. If you think a decision is wrong, open an issue first; don't change behaviour silently.
- **The plan is in [docs/plan/](docs/plan/README.md).** Work is split into batches, stages and tasks (`B3.2.1`). Current progress is in [docs/STATUS.md](docs/STATUS.md).
- Bugs and feature ideas: use the issue templates. Security problems: report them privately, never in a public issue.

## Setup

Requirements: a Mac with Apple silicon, macOS 14.2 or later, and Python 3 (for `tools/track.py`). Xcode requirements will be listed here once the project skeleton exists.

Enable the git hooks once per clone:

```
git config core.hooksPath .githooks
```

The hooks rebuild `docs/STATUS.md` and `docs/TIMELINE.md` before each commit, run `python3 tools/track.py check`, and validate the commit message. Never bypass them (`--no-verify`); if a hook blocks something legitimate, open an issue.

## Commit messages

```
B3.2.1: Add BS.1770 gating and integrated loudness

Why: <one or two lines>.

Task: B3.2.1
Decisions: #77, #78, #84
Evidence: Tech 3341 #1–#6 within ±0.03 LU; chunking test bit-identical
```

- **Subject:** imperative, at most 72 characters, starting with the task ID and a colon.
- **`Task:`** (required): a task ID, a backlog ID (`X3`), or `meta` for tracking and housekeeping only.
- **`Decisions:`** every decision ID the commit implements or touches.
- **`Evidence:`** required on the commit that marks a task `done`: the tests that pass and the numbers measured.
- One task per commit. Every commit leaves the build green.
- No co-author or "generated by" lines for tools of any kind. Commits are authored by the person submitting them.

## Branches and pull requests

- One branch per stage, created from `main`: `b3.2-loudness-analyser`.
- `main` changes only through pull requests, merged with a **merge commit** (never squash or rebase-merge: that would drop the per-task commits and their trailers).
- Commits must be signed.
- A pull request lists its tasks, the evidence, the decisions touched, and which modules it changes (see the modularity rule, DECISIONS.md §3.4).

## Changing a decision

Propose it in an issue: the problem, the options with their gains and costs, and how to test them against the standard method. Once the maintainer approves, the decision gets the next free number (from #173) and a row in DECISIONS.md §18.

## Tests and quality

- Run `python3 -m unittest discover -s tools` and `python3 tools/track.py check` before pushing.
- Never weaken a guard to get a green build: no disabled tests, lowered warning levels, loosened tolerances or skipped hooks.
- Measurement code must be verified against published standards or reference implementations (DECISIONS.md §4).
